A technical explainer for Python/Data Science developers learning TypeScript, React, Vite, and Zustand.

1. Mental Models for Data Scientists

1.1 React Components as Pure Functions + Side Effects

Think of every React component as a function that maps props + state → UI (JSX), similar to how matplotlib figures are functions of data. React re-runs this function whenever the "data" (state or props) changes — this is called re-rendering.

🐍 Python / Pandas Mental Model

def plot_sales(df):          # df = props
    fig = px.bar(df, x="day", y="amt")
    return fig               # JSX = fig

⚛️ React Component

function SalesChart({ data }) {  // data = props
  return <BarChart data={data} />;  // JSX
}

1.2 useState — Local Variables That Trigger Re-Renders

In Python you'd assign x = 5 and mutate it. In React, changing a local variable does NOT trigger a UI update. You need useState — think of it as a reactive cell in a Jupyter notebook: when the cell's value changes, everything downstream re-computes.

🐍 Python

count = 0
count += 1   # no UI update

⚛️ React

const [count, setCount] = useState(0);
// count = current value (read)
// setCount = setter (write)
setCount(count + 1);  // triggers re-render
Rule: Never mutate state directly (count = 5). Always call the setter (setCount(5)). This is like immutable data structures in pandas — you .copy() before modifying.

1.3 useEffect — "Run This After the Render"

React components should be pure functions during render. Side effects (fetching data, subscribing to events, writing to localStorage) must live inside useEffect. Think of useEffect as a scheduled callback that fires after the DOM has been painted — like a finally block or a contextmanager teardown.

🐍 Python Analogy

# Context manager that cleans up
with open('log.txt') as f:
    process(f)       # render
    # f.close()      # cleanup (auto)

# Scheduled callback
scheduler.run_after_main(
    lambda: save_to_db(df)
)

⚛️ React

useEffect(() => {
  // Side effect: runs AFTER render
  document.title = `Page ${id}`;

  return () => {
    // CLEANUP: runs before next
    // effect or on unmount
    console.log('cleaning up');
  };
}, [id]); // re-run when `id` changes

The dependency array [id] tells React: "re-run this effect whenever id changes". An empty array [] means "run once on mount" (like Python's if __name__ == "__main__").

1.4 Zustand Stores = Global Dataframes / State Dictionaries

Zustand is a lightweight state management library. Think of each Zustand store as a global dictionary (or pandas DataFrame) that lives outside the component tree. Any component can read from it (subscribe), and any component can write to it (dispatch actions). When the store changes, only the components that read that specific slice of state will re-render.

🐍 Python Mental Model

# A global dictionary that
# notifies listeners on change
global_state = {
    "results": {},
    "members": [],
}

def set_results(data):
    global_state["results"] = data
    notify_subscribers("results")

🌀 Zustand Store

// resultsStore.ts
const useResultsStore = create<ResultsState>()(
  persist(
    (set) => ({
      results: {},
      setResults: (data) =>
        set({ results: data }),
    }),
    { name: 'results',
      storage: createJSONStorage(
        () => sessionStorage
      ) }
  )
);

// Component reads a slice
const results = useResultsStore(
  (s) => s.results
);
Key insight: useStore(s => s.field) is like df[['col']] — you select only what you need, and re-computation (re-render) only happens when that column changes.

1.5 TypeScript Types = Dataset Schema Validation

TypeScript types are compile-time constraints on your code's "columns." Just as you validate a CSV's schema before analysis, TypeScript checks that every variable, parameter, and return value matches its declared shape — before the code even runs.

🐍 Python (Pandera / Pydantic)

import pandera as pa

class MemberSchema(pa.DataFrameModel):
    id: str
    name: str
    dob: str
    club: str

# Validates at runtime
df = MemberSchema.validate(csv_df)

📘 TypeScript Interface

interface Member {
  id: string;
  name: string;
  dob: string;
  club: string;
}

// Validates at compile time
// (before code runs)
const m: Member = JSON.parse(data);
//    ^ error if shape is wrong

2.3 The "Immutable Spread" Pattern (Critical Concept)

Zustand (and React) relies on immutable updates. You never modify an existing object — you create a new one. This is how React knows something changed: it compares references (oldObj !== newObj), not deep values.

Python equivalent: Using .copy() on a dict before mutating, or using dataclasses.replace(). In Zustand, you use the spread operator ... to achieve this.

🐍 Python

# Immutable dict update
old = {"a": {"b": 1}}
new = {
    **old,
    "a": {**old["a"], "b": 2}
}
# old["a"]["b"] is still 1

🌀 Zustand (this repo)

setResultsForScope: (date, event, gender, items) =>
  set((state) => ({
    results: {
      ...state.results,
      [date]: {
        ...state.results[date],
        [event]: {
          ...(state.results[date]?.[event] ?? {}),
          [gender]: items,
        },
      },
    },
  }))

3. The Build Pipeline — What Vite Does

3.1 Python Analogy: Why Build?

In Python, when you write pip install . or build a wheel, you're packaging your code into a distributable artifact. Vite does the same for web apps: it transforms your developer-friendly TypeScript/JSX source into optimized, minified JavaScript bundles that browsers can efficiently load.

Python ConceptWeb / Vite Equivalent
pip install -e . (editable install) npm run dev — development server with HMR, serves raw-ish source
python setup.py sdist bdist_wheel npm run build — produces a build/ folder of static assets
.whl file / .tar.gz build/client/ — HTML + JS + CSS bundles ready to deploy
Virtual environment (venv) node_modules/ — isolated dependency tree
requirements.txt / pyproject.toml package.json — declares dependencies and scripts
Bytecode compilation (.pyc) JSX → JS transpilation (by Vite/Rollup + esbuild)

3.3 Hot Module Replacement (HMR) — The Magic of Dev Mode

When you run npm run dev, Vite starts a development server. When you edit and save a .tsx file:

  1. Vite detects the file change via the file system.
  2. It only re-transpiles the changed module (via esbuild — extremely fast).
  3. It pushes the updated module to the browser via WebSocket.
  4. React replaces the component in-place — preserving local state (useState values are kept!).
Python analogy: Like Jupyter's %autoreload magic, but it preserves your notebook's runtime state. You change a function definition, and only that function reloads — all your variables stay intact.

4. Code Tour — The 3 Most Important Files

🥇 src/stores/resultsStore.ts

Job: The brain of the app. It holds the entire race results dataset as a nested dictionary (date → event → gender → MemberShort[]), provides an immutable setter that safely updates deeply nested scopes, and auto-persists to sessionStorage via Zustand's persist middleware so data survives page refreshes but not browser restarts.

Zustand TypeScript
🥈 src/pages/Results.tsx

Job: The primary user-facing page. It combines three Zustand stores (results, members, preregister) to render an interactive race-scoring panel with member autocomplete, drag-and-drop reordering, and a preregistered-member filter toggle. Demonstrates useMemo for derived data (filtered member lists) and useState for local UI state (the preregister checkbox).

React Zustand
🥉 src/utils/storageUtils.ts

Job: The I/O bridge. Reads user-uploaded JSON files (via FileReader) and writes them into Zustand stores; also serializes store state back out as downloadable JSON files (via Blob + programmatic <a> click). This is the file-system ↔ application-state boundary.
